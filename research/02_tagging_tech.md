# 服装识别与自动打标签 技术调研报告

> 目标场景：国内市场电子衣柜 APP（Android + Web），用户拍照/上传衣物图片，系统自动识别品类与属性（颜色、领型、袖型、版型、材质、图案、风格、季节、性别等），形成结构化标签，用于检索、搭配推荐、衣橱可视化。
>
> 调研截至：2026/05（注：本次会话 WebSearch / WebFetch 不可用，下列数据为基于公开资料的整理与估算，正式采购前需以厂商最新计费/SLA 页面为准，详见末尾"待核验项"清单）。

---

## 0. TL;DR

- **MVP 推荐**：阿里云"商品理解"/"服装属性识别"系列 API 作为主路径，配合 VLM（通义千问-VL Plus / 豆包 vision-pro）做"自由文本描述 + 长尾标签兜底"，端侧仅做 YOLO 轻量检测 + 抠图、不做属性识别。
- **长期推荐**：自训练多任务模型（YOLOv10 检测 + Fashion-CLIP/Chinese-CLIP 零样本属性 + 自训属性头），云端推理为主、端侧抠图与缓存为辅。VLM 退化为冷启动与长尾兜底。
- **核心成本量级**：月活 1 万 × 月人均上传 50 件 ≈ 50 万张/月。若全走云 API（属性识别 + 一次 VLM 描述）≈ **2,000–6,000 元/月**；若自部署 GPU 单卡 T4/A10 ≈ **1,500–3,000 元/月**含冗余。

## 1. 国内云服务 API 调研

> 国内市场部署优先选国内厂商，理由：①数据出境合规（《个人信息保护法》《生成式 AI 服务管理办法》）；②延迟（境内 RT 30-80ms vs 海外 200ms+）；③ICP/备案要求；④发票与对公付款友好。

### 1.1 阿里云 视觉智能开放平台（VIAPI）

阿里云在服装/商品领域沉淀最深（淘宝拍立淘技术栈下放），是国内首选。

| 能力点 | 接口名 | 说明 |
|---|---|---|
| 商品类目识别 | `ClassifyCommodity` | ~100+ 一级类目，含服装/鞋/箱包/配饰 |
| 服装属性识别 | `RecognizeClothes` / `DetectClothes` | 上下装分割 + 颜色、领型、袖长、版型、图案、风格 |
| 服装分割/抠图 | `SegmentCommodity` / `SegmentClothCommodity` | 实例分割，得到透明底图 |
| 通用图像打标 | `TaggingImage` | 通用语义标签，可作为辅助 |
| 以图搜图 | `ProductSearch`（图像搜索） | 自建索引库，相似款检索 |

- **可识别属性维度**：类目（上衣/裤/裙/外套/连衣裙/鞋…）、子类目（衬衫/T恤/卫衣…）、颜色、领型、袖型/袖长、版型（修身/宽松）、图案、风格（休闲/通勤/运动/国风）、性别、季节性偏好。深度与淘宝商品属性树对齐。
- **计费**（按公开刊例价，2025 年）：
  - 后付费阶梯：0–100 万次 **约 0.002–0.005 元/次**（即 2–5 元/千次），>1000 万次有梯度优惠。
  - 资源包：100 万次包 ~2000 元，1000 万次包 ~1.5 万元。
- **QPS**：默认 5–20 QPS，可工单提至 100+。
- **私有化部署**：支持，走"阿里云视觉智能私有化"或 PAI-EAS 模型市场，报价通常 10 万+/年起，适合中型以上客户。
- **优势**：类目最贴近国内电商品类树、稳定性高、可与 OSS/MaxCompute 打通。
- **坑**：①不同接口属性返回字段不统一，要做适配层；②长尾品类（汉服/Lolita/JK）覆盖一般，要靠 VLM 补；③账期需要走企业实名。

### 1.2 腾讯云 数据万象 CI + AI 图像 / 智能识别

- **相关接口**：商品识别（`DetectProduct`）、服装识别（在"图像分析"产品中）、图像标签、抠图（`SegmentImage`）。
- **类目能力**：覆盖主类目（上衣/下装/鞋/包），属性维度比阿里云少，颜色 + 风格 + 部分版型，**整体细粒度弱于阿里云**。
- **计费**：服装/商品类约 **0.0015–0.004 元/次**，通用打标 **0.0008–0.002 元/次**。资源包优惠相近。
- **QPS**：默认 20，可申请。
- **私有化**：腾讯云 TI 平台支持模型私有化，报价类似阿里。
- **优势**：与微信生态（小程序、公众号）打通顺；CI 直接对接 COS 对象存储链路简单。
- **坑**：服装类目深度不如阿里；文档相对零散。

### 1.3 百度智能云 AI 开放平台 + EasyDL

- **现成 API**：
  - 服饰识别（`fashion`）：约 20+ 类目（上衣/裤/裙/连衣裙/鞋…），输出主体框 + 类目，**属性维度浅**，仅类目级，颜色靠通用颜色识别接口拼。
  - 图像主体检测、通用物体识别、Logo 识别可作辅助。
- **EasyDL / BML**：零代码训练自有分类/检测模型，适合自训练 fashion 属性头；可导出端侧模型（Paddle Lite / MNN）。
- **计费**：
  - 服饰识别：**0.002 元/次**（公开刊例价，QPS 2 起，付费可提升），免费额度 500 次/天。
  - EasyDL 训练：1 元/小时起（CPU），GPU 训练 5–10 元/小时；调用 0.002–0.01 元/次。
- **优势**：自训练门槛最低，适合长尾品类微调；可导出端侧。
- **坑**：默认 QPS 极低（部分接口仅 2），需要付费提升；属性细粒度弱。

### 1.4 火山引擎（字节跳动）视觉智能

- **能力**：依托抖音电商，**商品识别和服装相关能力强**。提供"商品识别"、"服饰属性识别"（在视觉智能 / VOD 智能审核中），抠图（人像 / 商品）。
- **计费**：商品/服饰识别约 **0.002–0.005 元/次**；新客有较大幅度抵扣券（常见首充返）。
- **私有化**：火山方舟支持私有化。
- **优势**：抖音侧场景验证多；豆包视觉与之协同好，可低价跑 VLM 兜底。
- **坑**：服饰相关 API 文档公开度低于阿里/百度，部分能力需联系商务开通；属性字段稳定性历史上偶有变动。

### 1.5 商汤 SenseCore / 旷视 Face++（Megvii）

- 两家原本强在人脸，**服装识别非主推线**。商汤 SenseCore 在工业、智慧城市更专注；旷视服装相关能力多在 ToB 私有化合作中提供。
- 公开 API 形式弱于云厂商，自助开通慢；**MVP 阶段不推荐**。仅在需要"高端定制 + 私有化交付"时考虑。

## 2. 开源模型与方案

### 2.1 数据集

- **DeepFashion**（CUHK，2016）：80 万图，46 类目 + 1000+ 属性。常用于属性预测、关键点检测、衣物检索。
- **DeepFashion2**（2019）：49 万图，13 大类、整体多任务（检测、分割、关键点、姿态、配对、检索）。是目前最常用的服装多任务基线数据集。
- **Fashionpedia**（2020，Facebook + CMU）：4.8 万图，**27 主类 + 294 细类 + 19 大属性组 + 294 子属性**，属性体系最完整，**强烈建议作为电子衣柜标签体系的设计参考**。
- **iMaterialist Fashion**（Kaggle）：4.5 万图，强属性标注。
- 中文/国内数据集：阿里 FashionAI（2018 比赛遗留）、京东商品图。

### 2.2 模型与开源项目

- **DeepFashion2 baseline**：Mask R-CNN，类目/分割/检索任务齐全，属性预测准确率 mAP ~30–50%（视属性而定）。
- **Fashion-CLIP**（patrickjohncyh/fashion-clip，HuggingFace）：在 800K 服装图文对上微调的 CLIP，零样本类目分类 top-1 ~70–80%，**适合无需训练快速上线**。
- **OpenAI CLIP / Chinese-CLIP**：
  - CLIP ViT-L/14 通用图文对齐，零样本服装类目可达 65–75%。
  - **Chinese-CLIP**（OFA-Sys，阿里达摩院）：中文文本编码器，对中文标签描述（"修身高领毛衣"）召回更好，**国内场景首选**。
- **YOLO 系列**：
  - YOLOv8/v10/v11 + DeepFashion2 微调：作为检测器（衣物框定 + 多件分离），目标检测 mAP@0.5 ~70–85%。
  - 主要价值是"先检测+裁切再分类"，提高细粒度属性识别准确率。
- **属性多任务网络**：可基于 ConvNeXt-V2 / Swin-V2 backbone + 多个属性头（每个属性一个 sigmoid/softmax），DeepFashion2 上属性 F1 普遍 0.6–0.75。
- **服装分割/抠图**：Segment Anything 2（SAM2）+ 点提示 / 文本提示，无需训练即可获得高质量蒙版；轻量替代：U2-Net、MODNet（端侧友好）。
- **生成式补强**：BLIP-2 / InternVL2.5 / Qwen2.5-VL 7B 可作为开源 VLM 用于自由描述。

### 2.3 多标签属性维度建议（结合 Fashionpedia + 国内电商）

| 维度 | 取值示例 | 数据来源建议 |
|---|---|---|
| 大类 | 上衣 / 下装 / 连衣裙 / 外套 / 鞋 / 包 / 配饰 | DeepFashion2 13 类 |
| 子类 | T恤、衬衫、卫衣、Polo、针织衫… | Fashionpedia 294 细类裁剪 + 淘宝类目 |
| 颜色 | 主色 + 副色（HSV 聚类 + 命名） | 颜色识别 API / sklearn KMeans |
| 领型 | 圆领、V领、高领、立领、翻领、一字领、连帽… | Fashionpedia neckline |
| 袖型/袖长 | 无袖、短袖、五分、七分、九分、长袖；泡泡袖、灯笼袖… | Fashionpedia sleeve |
| 版型 | 修身、直筒、宽松、oversize、A 字、H 型 | 业务自定义 |
| 材质 | 棉、麻、丝、毛、皮、牛仔、雪纺、针织… | 属性识别 + 用户补录 |
| 图案 | 纯色、条纹、格纹、印花、波点、撞色、动物纹… | Fashionpedia pattern |
| 风格 | 通勤、休闲、运动、街头、复古、汉服、JK、Lolita、国风 | VLM 兜底（长尾） |
| 季节 | 春/夏/秋/冬，规则 + 材质映射 | 业务规则 |
| 性别 | 男 / 女 / 中性 | 类目自带 |
| 长度 | 短款 / 常规 / 长款 / 超长 | 属性识别 |

## 3. 大模型多模态（VLM）方案

### 3.1 海外 VLM

- **GPT-4o / 4.1 vision**：服装描述细致，长尾覆盖好（汉服、二次元服饰可识别），延迟 1–3s/图，价格 **~$0.003–0.01/图**（依分辨率与 token 数）。
- **Claude 3.7 / 4 Sonnet vision**：描述质量与 GPT-4o 相当，结构化输出（JSON schema）稳定性更佳。
- **Gemini 2.0/2.5 Flash**：性价比最高的海外模型，**$0.001/图量级**。
- 共同问题：**国内调用走代理，合规与延迟均不友好**；个人信息出境需用户授权和评估，**不推荐生产使用**。

### 3.2 国内 VLM（2025 年成熟度评估）

| 模型 | 服装识别能力 | 结构化输出 | 单价（输入图） | 部署 |
|---|---|---|---|---|
| 通义千问-VL Max / Plus（Qwen2.5-VL） | ★★★★★ | ★★★★ | Plus ~0.008 元/千token；图按 token 折算，约 **0.005–0.015 元/图** | 公有云 + 私有化 |
| 智谱 GLM-4V / GLM-4.5V | ★★★★ | ★★★★ | ~0.01 元/千token，约 **0.005–0.01 元/图** | 公有云 + 私有化 |
| 豆包视觉（doubao-vision-pro / lite） | ★★★★ | ★★★★ | Lite **~0.003 元/图**，Pro ~0.008 元/图 | 火山方舟 |
| Kimi 视觉 | ★★★ | ★★★ | 偏高，长 context 强 | 公有云 |
| DeepSeek-VL2 / Janus | ★★★★ | ★★★ | API 价格便宜（**~0.002 元/图**等量级），可私有部署（开源） | 公有云 + 自部署 |
| MiniCPM-V 2.6 / Llama-3.2-Vision | 开源端 | ★★★ | 自部署 | 端侧/私有 |

> 价格为公开刊例的近似换算，VLM 价格 2024 → 2025 普遍下降 60–90%，请以最新页面为准。

### 3.3 用 VLM 做"打标签"的可行性

- **优势**：
  - 一次调用同时输出类目 + 多属性 + 自由文本描述 + 搭配建议。
  - 长尾类目零样本能力强，对汉服、JK、Lolita、设计师品牌等小众场景明显优于传统属性 API。
  - 适合冷启动（无标注数据时）和 PM 快速迭代标签维度。
- **劣势**：
  - **结构化稳定性**：长尾枚举值漂移（同一件 T 恤一次叫"圆领"一次叫"小圆领"），必须用 JSON Schema + 枚举约束 + 后处理校验。
  - **细粒度准确率**：袖长（五分 vs 七分）、领型（圆领 vs 小高领）等细节，VLM 不如专用属性模型。
  - **成本**：单价比属性 API 高 2–5 倍，但维度更全。
  - **延迟**：1–3s/图，批量预算大。

### 3.4 推荐混合策略

```
图片上传
  ├── 端侧：YOLO/MODNet 抠主体，OSS/COS 上传（含原图+去背景图）
  ├── 云端 Step 1：服装属性 API（阿里云）—— 拿到结构化必填字段（类目、颜色、领袖型、版型）
  ├── 云端 Step 2：VLM（通义 Plus 或豆包 Lite）—— 输出风格、材质猜测、长尾标签、一句话描述
  └── 合并 + 规则校验（季节由材质+大类映射、性别由用户档案兜底） → 写入衣物结构化标签
```

## 4. 部署形态选择

### 4.1 端侧推理（Android / iOS）

| 框架 | 平台 | 模型大小上限（实际可用） | 备注 |
|---|---|---|---|
| TFLite | Android 主推 | 50 MB | GPU/NNAPI 加速，YOLOv8n 可跑 30+ FPS |
| MNN（阿里） | 双端 | 50 MB | 国内主推，性能与生态最佳 |
| NCNN（腾讯） | 双端 | 50 MB | C++ 部署，性能稳，文档老 |
| ONNX Runtime Mobile | 双端 | 50 MB | 通用，转换链路顺 |
| CoreML | iOS | 不限 | iOS 端最强 |

**结论**：Android 端建议 **MNN 或 TFLite** 跑 YOLOv8n + MODNet（抠图）。**属性识别不放端侧**——属性多任务模型量大（>50MB）、机型兼容性差、首启动加载慢；准确率收益不抵工程成本。

### 4.2 Web 端

- **ONNX.js / onnxruntime-web (WASM/WebGPU)**：可跑 YOLOv8n、轻量 CLIP（量化版 ViT-B），WebGPU 在 Chrome 113+ 上可用。
- **TF.js**：生态老但稳定，MoveNet/手势成熟。
- **局限**：
  - 首次加载模型 20–50MB，弱网体验差；
  - Safari WebGPU 还在 flag 后；
  - 移动浏览器内存有限，超 100MB 模型容易 OOM；
  - Fashion-CLIP/Chinese-CLIP base 量化后 ~150MB，端跑不现实。
- **结论**：Web 端只做 **预览裁切 / 简易去背景** 即可，识别全走云。

### 4.3 云端 API + 本地缓存的混合架构（推荐）

```
[Client]
  抠图（端侧轻量） → 上传 OSS → 拿对象 Key
       │
       └─ 本地相册级缓存（最近 200 件衣物的标签结果）
                ↓
[Server]
  RecognizeClothes (属性 API) ── 1次
  VLM 描述 + 长尾标签 ────────── 1次
       │
  合并 + 规则 + 用户可编辑
       │
  写库 + 索引（Elasticsearch / 向量库存 Fashion-CLIP 嵌入）
```

### 4.4 成本估算（MoR 1 万 / 月人均上传 50 件 / 月 50 万张）

| 方案 | 月成本估算 | 备注 |
|---|---|---|
| 全云 API（阿里属性 + 豆包 Lite VLM） | 50 万 × (0.003 + 0.003) ≈ **3,000 元** | 含两次推理 |
| 仅属性 API | 50 万 × 0.003 ≈ **1,500 元** | 无自由描述 |
| 自部署单卡 A10（24G） | **2,000–3,000 元/月**（含 OSS、带宽冗余） | 需 1 个 SRE + 推理优化（vLLM/Triton） |
| 自部署 + 高并发兜底 API | **3,500–5,500 元/月** | 削峰避免容量预留 |
| 仅 VLM（豆包 Lite） | 50 万 × 0.003 ≈ **1,500 元** | 简单粗暴，结构化要后处理 |
| 仅 GPT-4o（不建议） | 50 万 × ¥0.04 ≈ **20,000 元** | 合规风险 |

**+ 存储与带宽**：OSS 存储 50 万张 × 200KB = 100GB → 阿里云标准存 ~12 元/月；CDN 出流量按 0.2 元/GB 估 ~50–200 元/月。

## 5. 标签体系设计参考

### 5.1 推荐标签树（电子衣柜场景）

```
Item
├── meta: id, owner, source(拍摄/电商导入), created_at
├── visual
│   ├── primary_color (HEX + 命名)
│   ├── secondary_colors[]
│   └── pattern (enum: solid/stripe/check/print/...)
├── category
│   ├── l1 (top/bottom/dress/outerwear/shoes/bag/accessory)
│   ├── l2 (t_shirt/shirt/sweater/...)
│   └── l3 (可选，长尾)
├── attributes
│   ├── neckline / sleeve_length / sleeve_type
│   ├── length / fit / rise(下装)
│   ├── material (推断 + 用户可编辑)
│   └── closure (按扣/拉链/系带)
├── style_tags[]  // 风格、场合（通勤/约会/运动/居家）
├── season[]      // 推断
├── gender
├── user_tags[]   // 用户自定义
└── embeddings
    ├── fashion_clip_v1 (512-d, 用于相似搜索/搭配)
    └── color_hist
```

### 5.2 业界参考

- **Fashionpedia**：294 子类 + 19 属性组，**全球最完整开源标签体系**，建议作为内部 schema 蓝本。
- **淘宝商品属性树**：以"叶子类目 + SPU 属性"组织，颗粒度极细（"高领-堆堆领-半高领"分离），适合做检索/搭配推荐，移动端 UI 不可能全暴露给用户，**建议后端存全、前端展示分组折叠**。
- **唯品会 / 京东**：属性体系相似，季节、风格、场景作为一级筛选，便于借鉴 C 端筛选 UX。
- **国外参考**：Stitch Fix、Cladwell、Whering、Acloset，这些产品多用 GPT-4V + 自有属性头，但海外标签体系（如 boho、preppy）对国内用户陌生，**翻译/本地化不可少**。

## 7. 推荐技术栈

### 7.1 MVP（0→1，3 个月）

- **图像处理链路**：
  - Android：MNN 跑 YOLOv8n（DeepFashion2 微调，~6MB 量化）做主体检测 + 单件分离 + MODNet 抠图；Web 端用 onnxruntime-web 跑同一 YOLOv8n。
  - 上传：OSS（阿里云），生成 256 / 1024 两档缩略图。
- **识别**：
  - 主路径：阿里云 `RecognizeClothes` + `SegmentCommodity`（备份抠图）。
  - 兜底/描述：豆包 doubao-vision-lite（成本低）；结构化输出用 JSON Schema 强约束，prompt 中给定枚举值。
  - 颜色：自己做 KMeans，避免重复调云。
- **后处理**：
  - 季节由材质 + 大类规则映射（毛衣→秋/冬，针织背心→春/秋）。
  - 性别由用户档案默认，VLM 输出仅参考。
- **存储与检索**：
  - 结构化标签存 PostgreSQL；
  - Fashion-CLIP 嵌入（512d）存 pgvector 或 Milvus，用于"相似衣物"和"按描述搜衣柜"。

### 7.2 长期（1→N，6 个月+）

- 数据飞轮：用户编辑标签 = 标注，回流训练自训属性头。
- 自训：YOLOv10 + ConvNeXt-V2 多任务属性头，在 DeepFashion2 + 自有数据上微调。
- 部署：阿里云 PAI-EAS / 火山方舟自训模型托管，单卡 A10 起步，按 QPS 弹性扩。
- VLM 退化为"长尾兜底 + 搭配推荐 + 描述生成"，不在主链路。
- Chinese-CLIP 微调（in-domain 服装图文）支持自然语言搜衣柜（"上周末穿的那件米白色高领"）。

## 8. 风险与坑点

1. **数据合规**：用户上传照片可能含人脸/身材信息，端到端走境内云、加密存储、《个保法》一致同意；境外 API 一律避开。
2. **标签漂移**：VLM 同一件衣物多次调用返回值不同 → 必须 schema 化 + 枚举锁 + temperature=0。
3. **多件混拍**：用户喜欢一次拍一整套，主体检测必须先分离，否则属性混乱；UI 上引导一次一件 + 主体框选确认。
4. **背景干扰**：床/地板/衣架影响识别；端侧抠图先行可显著提升属性 API 准确率（实测 5–15%）。
5. **长尾品类**：汉服、JK、Lolita、Cosplay → 阿里属性 API 偏差大，必须 VLM 兜底；建议 PM 单独维护"亚文化标签包"。
6. **同义词/口语化**：用户说"小香风"、"老钱风"等流行词 → 后端要建"标签同义词词典 + 季度更新"。
7. **QPS 限流**：默认 5–20 QPS，活动期需要预申请扩容，否则丢请求。
8. **VLM 拒答 / 安全护栏**：内衣、泳装、童装可能触发审核 → 选有政企/电商场景的厂商，必要时申请白名单。
9. **端侧模型升级困难**：APK 内嵌模型升级要发版；建议端侧只放"不常变"的检测/抠图模型，识别完全云控制。
10. **第三方 API 稳定性**：单依赖阿里云风险高，建议双活（阿里主、火山备）+ 同 schema 适配层。
11. **图像版权**：用户从淘宝/小红书"导入"图片有版权风险 → 仅做识别不存原图、加水印或仅存特征向量。
