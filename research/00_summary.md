# 00 · 研究汇总：电子衣柜APP（Android + Web 双端）

> 调研时间：2026-05-25 · 国内市场 · 详细数据见同目录的 `01_competitors.md`、`02_tagging_tech.md`、`03_segmentation_tech.md`、`04_users.md`

---

## TL;DR

1. **市场机会真实存在但拥挤**：国内有搭搭(200万)、尽简衣橱、氢气、胶囊衣橱等 8+ 个产品，海外 Whering/Acloset/Stylebook/Indyx 已成熟。**所有现有产品共同弱点 = 录入门槛极高**，用户录到 20-30 件就放弃。
2. **「全身照→分部位单品」是真空白市场**：搜遍国内外 20+ 款衣柜 APP，**没有一家把这个功能做成核心卖点**。技术成熟（阿里云服饰分割 API 已支持外套/上装/裤装/裙装/帽/鞋/包），但产品化空缺。这是我们最强的差异化卖点。
3. **技术栈基本清晰**：
   - 后端：阿里云 VIAPI（属性识别）+ VLM（豆包/通义千问-VL）兜底 + 自部署 SCHP/SegFormer-B2-clothes 做分部位裁剪 + RT-DETR-seg 做实例分离（避开 YOLO AGPL 协议）
   - 跨端：单一 FastAPI/Node 后端 + Android 原生（Kotlin/Compose）+ Web（React/Next.js）+ 共享 OpenAPI 类型
   - MVP 月成本估算：1 万 DAU、人均 50 件/月 ≈ **¥3,000–4,000/月**（云 API + OSS + CDN，不含人力）
4. **最大商业风险是「跑路恐慌」**：衣橱日记停运、胶囊衣橱永久会员数据丢失，让用户对付费极度谨慎。必须做好**数据可导出、免费 tier 永远可用**。

## 一、差异化定位建议

### 我们的核心价值主张

> **"一张全身照，自动入柜 5 件衣服"** — 把现有衣柜 APP 录入门槛降低 5-10 倍。

### 与现有产品的差异化矩阵

| 维度 | 搭搭（最强对手） | Indyx（海外标杆） | **我们** |
|------|-----------------|-----------------|---------|
| 一件件拍照 | ✅ AI 抠图 | ✅ AI 抠图 | ✅ |
| 电商链接导入 | ✅ | ✅ | ✅（淘宝/京东） |
| **全身照分部位录入** | ❌ | ❌（用 $295 人工） | ✅ **★ 核心卖点** |
| AI 搭配 | ✅ 天气联动 | ⭐ 人类 stylist 服务 | MVP 不做，避免"鸡肋" |
| 平台覆盖 | iOS+Android | iOS+Android | **Android + Web** 并行 |

### 三层产品故事

1. **入门钩子**：「拍一张全身照，自动入库 5 件衣服」 — 解决最痛的录入摩擦
2. **核心粘性**：穿着次数统计 + 季节性提醒 + 月度衣橱报告 — 让用户愿意定期打开
3. **付费转化**：高清抠图导出、AI 搭配灵感、跨设备同步、cost-per-wear 看板

## 二、技术栈建议（兼顾 Android + Web 跨端）

### 整体架构

```
┌──────────────────┐   ┌──────────────────┐
│  Android (Kotlin │   │  Web (Next.js +  │
│   + Compose)     │   │   React + ts)    │
└────────┬─────────┘   └────────┬─────────┘
         │   共享 OpenAPI 契约   │
         └──────────┬───────────┘
                    ▼
    ┌───────────────────────────────────┐
    │  FastAPI / Node BFF（业务后端）    │
    │  - 鉴权、衣物 CRUD、搭配、统计      │
    └──────────┬───────────┬────────────┘
               ▼           ▼
   ┌──────────────────┐ ┌──────────────┐
   │  AI 推理服务      │ │ OSS/CDN/DB   │
   │  (Python+GPU)    │ │ MySQL/Redis  │
   └──────────────────┘ └──────────────┘
```

**为什么这样分**：
- 双端共享同一套 OpenAPI（用 schema 自动生成 Kotlin/TypeScript 类型），降低跨端不一致
- 业务后端用 Node 或 FastAPI 都可，但 **AI 推理独立成 GPU 服务**（Python + Triton/vLLM），避免业务后端被 GPU 推理拖死
- 不推荐 React Native / Flutter 做核心 — Android 的相机/拍照体验对识别质量太关键

### AI 流水线（MVP→进阶）

#### 流水线 A — 单件拍照录入（基线，参考搭搭）

```
拍照 → 端侧 MNN/NCNN 跑 MODNet 抠图 → 上传 → 
   阿里云 VIAPI RecognizeClothes（类目+属性）→ 
   豆包 VLM 兜底长尾标签（汉服/JK/IP 联名）→ 
   入库
```
- 单价：约 **¥0.003–0.008/件**（含 VLM 兜底）
- 端侧抠图保护用户隐私，云端只识别类目属性

#### 流水线 B — 全身照分部位裁剪（差异化卖点）

```
全身照 → 服务端 GPU 上 SCHP-ATR(18类) 主分割 → 
   RT-DETR-seg + DeepFashion2 二次实例分离（处理上衣+外套粘连、左右鞋）→ 
   按部位 crop → BiRefNet 二次抠图去残留背景 → 
   每件单品自动跑流水线 A 的属性识别 → 
   入库 + 推送给用户确认（"识别到上衣/外套/裤/鞋/包，是否全部加入？"）
```
- 单次成本：约 **¥0.05–0.10/张全身照**（含分割+多件识别）
- **关键**：不要用 YOLOv8 — **YOLOv8 是 AGPL-3.0**，闭源商用必须改 RT-DETR 或购买 Ultralytics Enterprise（约 $10k+/年）

### 跨端复用清单

| 复用类型 | 实现方式 |
|---------|---------|
| API 契约 | OpenAPI 3.0 + openapi-generator 生成 Kotlin DTO 和 TS 类型 |
| 业务校验规则 | 后端为唯一真相源，前端只做 UI 层校验 |
| 图片处理逻辑 | 抠图/分割在后端统一，前后端只传 URL |
| 国际化文案 | 共享 JSON 文件 + 各端加载 |
| 设计令牌（颜色/字号） | Figma → Style Dictionary → 双端导出 |

### 推荐 SaaS 与开源组件

| 角色 | 推荐 |
|------|------|
| AI 主推理 | 阿里云 VIAPI + 阿里云 GPU 自部署 SCHP |
| VLM 兜底 | 豆包 vision-lite（¥0.003/张，国内合规友好） |
| 对象存储 | 阿里云 OSS + CDN |
| 数据库 | 阿里云 RDS MySQL（主）+ Redis + pgvector（语义检索，备） |
| 鉴权 | 微信登录、手机号一键登录、AppleID |
| 监控 | 阿里云 ARMS、Sentry |
| Web 部署 | 阿里云 ECS / 函数计算 + CDN |
| 客户端崩溃 | Bugly（Android）、Sentry（Web） |

## 三、商业化策略

### 免费 / 付费分层（基于国内用户心智）

| 功能 | 免费 | 会员（¥18/月 或 ¥98/年 或 ¥298 买断） |
|------|------|--------------------------------------|
| 单件衣物上传 | 无限 | 无限 |
| 全身照分部位录入 | 5 次/月 | 无限 |
| 自动识别+打标签 | 基础类目 | 完整属性（含 VLM 长尾） |
| AI 搭配灵感 | 3 套/天 | 无限 + 天气联动 |
| 穿着次数统计 | ✅ | ✅ |
| 月度衣橱报告 | ❌ | ✅ |
| 多端同步 | ❌（仅本设备） | ✅ |
| 数据导出 ZIP | ✅（永远免费，建立信任） | ✅ |
| 高清抠图导出 | 普通画质 | 4K 无水印 |
| 闲鱼/转转一键挂卖 | ❌ | ✅ |

**关键原则**：
- **免费 tier 必须覆盖刚需** — 让"录入+查看+基础统计"永远免费，用户才敢深度录入
- **付费在「省时间」和「数据洞察」**，不在「让你能用」
- **永远不下架免费数据导出** — 用「不绑架数据」对冲跑路恐慌

### 增值服务方向（远期）

1. 远程穿搭咨询（人类造型师 1v1）— 参考 Indyx Lookbook ¥150/次国内对标 ¥99–199
2. 上门代录入服务（一线城市） — 类比 Indyx $295 In-Home，国内可做 ¥299–499
3. 与电商 CPS 联动 — 用户买的同款分成（淘宝/京东客）

## 四、关键风险与缓解

| 风险 | 严重度 | 缓解 |
|------|--------|------|
| **AI 识别准确率不够，全身照拆错** | 高 | 用户确认环节、用 SCHP-ATR + DeepFashion2 双模型融合、上线前在 500 张样本上达到 ≥85% 准确率 |
| **YOLOv8 协议踩雷** | 高 | 改用 RT-DETR-seg 或 Mask R-CNN（Apache 2.0），上线前过法务 |
| **数据合规（个人信息保护法）** | 高 | 数据境内闭环、用户隐私协议、人像照可选本地处理、获取生成式 AI 备案 |
| **用户"跑路"恐慌** | 中 | 数据一键导出 ZIP（永久免费）、公开技术栈、官网公告"运营至少 5 年" |
| **拍照真实环境差，识别效果差** | 中 | UI 提供拍摄指引 + 多角度提示、自动质量检测（模糊/光线弱时提示重拍） |
| **录入完成后失活（"3周魔咒"）** | 中 | 每日穿搭 push、周报、季节性活动（换季整理打卡） |
| **大厂入局（阿里 Lookie 已是信号）** | 中 | 差异化在「衣橱管理 vs 试衣」+ 「全身照分部位录入」垂直深耕 |
| **AI 推理成本爆炸** | 低 | 端侧抠图、属性结果缓存、低活跃用户降级到便宜模型 |

## 五、下一步行动建议

### Phase 0（1-2 周）：技术验证

1. **POC：全身照分部位裁剪**
   - 找 30-50 张真实全身照（含坐姿/侧身/低光等边缘场景）
   - 跑通 SCHP-ATR + RT-DETR-seg + BiRefNet 流水线
   - **必须达到 ≥85% 准确率**才进入下一阶段，否则要重新评估技术方案
2. **阿里云 VIAPI 服装属性识别精度测试** — 在自己的样本上测，看实际效果
3. **法务确认 AGPL 协议影响**，确定模型选型

### Phase 1（4-6 周）：MVP 最小可用版

1. 后端：用户系统 + 衣物 CRUD + OSS 接入 + 阿里云 VIAPI 集成
2. AI 服务：单件识别流水线（流水线 A）+ 全身照分部位流水线（流水线 B）
3. Web 端：录入、衣柜浏览、单品详情、按属性筛选
4. Android 端：拍照录入、衣柜浏览、单品详情（功能与 Web 对齐）
5. 不做：AI 搭配、社交、电商联动（避免分散精力）

### Phase 2（4 周）：粘性功能

1. 穿着次数统计、月度衣橱报告
2. OOTD 记录、可分享小红书的卡片模板
3. 数据导出 ZIP（关键信任功能）

### Phase 3（按市场反馈节奏）：增值与变现

1. AI 搭配灵感（shuffle 模式，半自动，不吹"智能"）
2. 会员体系上线
3. 微信/支付宝支付接入
4. 闲鱼/转转挂卖联动

### 不建议在 MVP 阶段做的事

- ❌ AI 自动搭配（用户公认"鸡肋"，不如做半自动 shuffle）
- ❌ 虚拟试穿（成本高、体验未必好、目前还是噱头）
- ❌ 社交功能（DAU 不到 5 万社交没意义，前期反而是负担）
- ❌ 复杂会员体系（先一个买断或一个月费，简化决策）
- ❌ 跨平台框架（React Native/Flutter） — Android 拍照体验对识别质量太关键

## 六、关键开放问题（需要你定）

1. **团队配置**：你是单人开发还是有团队？是否有 AI/算法工程师？这决定 Phase 0 POC 谁来跑
2. **资金预算**：MVP 阶段 ¥3-5 万的服务器+API+第三方服务月度成本是否在预算内
3. **上线时间窗**：3 个月 MVP / 6 个月公测 / 12 个月正式商业化 — 节奏期望
4. **首批种子用户**：你身边有没有 10-50 个可以试用的用户？小红书/微信群冷启动渠道
5. **是否要做小程序**：当前没规划，但微信小程序是国内重要分发渠道，是否在 Phase 2 加入
6. **如何处理人像隐私**：全身照含人脸，要做模糊或本地预处理吗？

回答这几个问题后，我可以进入「Phase 0 详细执行计划」或者直接开始搭项目骨架。
